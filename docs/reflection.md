# Failure Analysis

## Objective

Document situations where the system produced incorrect, incomplete, or unexpected results and analyze the likely causes.

---

## Issue 1 – Resume Fit Score Variation

### Observation

The generated resume fit score was reasonable but subjective. Running the advisor multiple times may produce slightly different scores while keeping similar strengths and recommendations.

### Likely Cause

The fit score is generated by an LLM rather than a deterministic scoring algorithm. Small variations in the model's reasoning can change the numerical score without significantly affecting the overall assessment.

### Impact

Low.

The recommendations and overall assessment remained consistent even when the exact score could vary.

---

## Issue 2 – Company Website Availability

### Observation

Some job postings did not include an official company website.

As a result, the WHOIS lookup could not provide additional legitimacy information.

### Likely Cause

The system only extracts information explicitly available in the job posting and does not attempt to infer or search for missing company websites.

### Impact

Medium.

The legitimacy assessment relied primarily on the job posting and Tavily web search instead of WHOIS data.

---

## Issue 3 – Skill Categorization

### Observation

Some technologies were grouped together or summarized instead of being listed individually.

For example, multiple testing technologies or related frameworks were combined into broader categories.

### Likely Cause

The LLM summarizes semantically similar information instead of reproducing every keyword exactly as written in the job posting.

### Impact

Low.

The extracted information remained useful for market analysis and gap identification, although a few individual technologies may not appear separately.

# Reflection

## 1. Workflows, Agents, or Hybrid

I structured the project as a hybrid of workflows and agents.

Phase 1 and Phase 2 are mainly workflows because their steps are predictable. Phase 1 extracts job information, researches companies, and creates the market analysis. Phase 2 extracts the resume and compares it with the market analysis.

Phase 3 uses more agent-like behavior because the application needs to investigate the company and job posting using web search and WHOIS before producing the final recommendation.

I chose this approach because the first two phases are easier to control with a fixed workflow, while Phase 3 benefits from tools and investigation.

---

## 2. Prompt Engineering

The main prompt choices that improved consistency were clearly defining the required fields and telling the model to return only the structured output.

I also told the model not to guess information that was not present in the source. Missing information was represented with null values or empty lists.

For the market and resume analysis, I explicitly listed the information that needed to be identified. This helped keep the outputs consistent across different job postings and resumes.

---

## 3. Legitimacy Agent

The legitimacy assessment uses web search and WHOIS information to check whether a job posting and company appear trustworthy.

The main signals I prioritized were the company's web presence, whether the job could be verified, the company domain, WHOIS registration information, matching contact information, and possible red flags such as requests for personal information or unusual compensation.

The main limitation is that some WHOIS information is hidden by privacy services, and some job postings do not provide enough company or domain information. Because of this, the legitimacy result should be treated as a recommendation rather than a guarantee.

---

## 4. Models and Cost

I used Google Gemini 2.5 Flash through OpenRouter for the LLM calls.

I chose this model because the project required multiple LLM calls for job extraction, resume extraction, market analysis, gap analysis, and the application advisor. Using a fast and lower-cost model helped keep the OpenRouter usage within the available budget while still producing useful structured results.

I also reused the same LLM service across the phases instead of creating separate clients for each phase.

---

## 5. Coding Agent Process for Phase 3

For Phase 3, I used Codex as the coding agent.

My initial instruction was to build the Application Advisor using the existing Phase 1 and Phase 2 code. I asked it to reuse the existing job extraction, LLM service, PDF extraction, resume analysis, and Tavily search functionality instead of creating everything again from scratch.

The development took several iterations. I reviewed the generated code after each iteration, ran the application, and made changes when something did not work as expected.

The coding agent correctly helped build the Phase 3 structure, application report model, advisor workflow, WHOIS service, HTML report generation, and CLI integration. It also reused several components that were already working from the earlier phases.

I manually fixed issues related to the existing project structure, imports, generated outputs, and some implementation details after testing the application. I also simplified parts of the generated code when they were more complicated than what was required for the assignment.

Overall, Codex was useful for creating the first working version of Phase 3 and speeding up the implementation. However, I still had to review the code, run it, debug errors, and make manual corrections to make sure it matched the assignment requirements.

---

## 6. Other AI Tools Used

I used ChatGPT during development to help understand the assignment requirements, plan the project structure, debug errors, and review implementation decisions.

For example, it helped me identify issues with JSON generation and the Phase 2 dependency on the market analysis file.

It also produced suggestions that needed to be corrected or simplified. In some cases, suggestions included extra code or functionality that was not required by the assignment, so I removed those parts and kept the implementation minimal.

The main lesson was that AI tools were useful for development and debugging, but the generated code still needed to be reviewed and tested against the assignment requirements.
